# 万卡 GPU 集群监控、故障分类与处置总结

返回 [本篇导航](./README.md)。来源为用户提供的 16 页 PDF，发表于 2026-10-25；下文 p.N 指 PDF 页脚页码。本文区分“原文建议”“本平台已观测到的数据”“个人判断”，未修改平台监控或执行故障处置。

## 1. 一句话总结

先按任务、GPU、网络、链路四个平面收集证据，再按五类故障选择定位与恢复路径；以同配置基线、事件日志和跨节点对比补齐周期指标的盲区，最后再调通信、存储和调度。

## 2. 背景、核心思想与证据边界

文章讨论万卡集群在任务中断、慢节点和通信 Hang 中损失有效算力的问题。开篇给出作者案例：2048 卡任务 MFU 从约 38% 恢复至 45%，根因是一个节点 8 卡 SM Clock 约 1.1GHz，其他节点约 1.9GHz（p.1）。这是文章报告的案例，本次没有复现实验。

核心方法是从任务症状向底层定位，按时间戳对齐任务日志、GPU 指标、网络计数和链路事件；网络干净不代表 GPU 正常，利用率高不代表训练在推进。

## 3. 监控四平面：看什么、从哪里采、当前平台能对应什么

| 平面 | 原文关注指标 | 采集方式与定位入口 | 本次 AOM 快照覆盖与缺口 |
|---|---|---|---|
| 任务 | MFU、samples/sec、step 耗时及方差、loss、日志最后更新时间；初始化/step/epoch 锚点 | 用户日志、K8s Event、Prometheus；对齐各 Rank 的 Init COMPLETE 时间（p.2–3） | 本次只扫描 DCGM/GPU 命名及健康检查，未验证任务进度、MFU、日志或事件采集；GPU_UTIL 不能替代 MFU |
| GPU | 引擎活跃度、SM Active/Occupancy、Tensor Active、SM Clock、显存、Xid、NVLink 吞吐及拓扑 | DCGM、nvidia-smi、dmesg、topo -m（p.3–4） | 已发现 GR_ENGINE_ACTIVE、SM_ACTIVE/OCCUPANCY、PIPE_TENSOR_ACTIVE、SM_CLOCK、FB_*、XID_ERRORS、NVLink 指标；需逐集群核实有效样本 |
| 网络 | PFC、ECN、队列深度、headroom、CNP Slow Restart、RDMA 重传和网卡速率 | 交换机计数、ethtool -S、rdma stat；无损优先级与默认队列对照（p.4–5） | 已观察 ib/roce 健康检查名称，但未验证 PFC/ECN/headroom/CNP/RDMA 原始指标；不能因为本次正则未返回就认定整个平台没有 |
| 链路 | CRC、收发光功率、BER/FEC、端口翻转、LLDP、GPU/网卡拓扑 | ethtool -S/-m、交换机接口状态、nvidia-smi topo -m；交付/变更存基线（p.5） | 有 PCIE_REPLAY_COUNTER/LINK_WIDTH、P2P 状态及 nvlink_status/pcie_aer 等检查名；CRC/DDM/BER/LLDP 未核实 |

### 3.1 四个 GPU 活跃度指标的组合读法（p.3，表 2）

| 原文组合 | 原文推断 | 下一步验证 |
|---|---|---|
| 引擎利用率、SM Active、Tensor Active 都低 | 数据加载/CPU 预处理不足 | DataLoader、num_workers、/dev/shm、CPU |
| 引擎利用率高，SM Active/Tensor Active 低 | 通信占比高、GPU 等数据 | NVLink/网卡吞吐、AllReduce 耗时 |
| 引擎利用率接近 100%，SM/Tensor 接近 0 | NCCL Hang 或等待 | NCCL 日志、Rank 进度与集合通信序号 |
| 引擎利用率高、SM Active 高、Tensor 低 | 非矩阵计算占比较高 | 算子构成与 profiler |
| 前两者高，Tensor Active 超过 50% | 作者认为算力接近吃满 | 仍应结合模型、精度、roofline/MFU 判断，不按 50% 统一停止优化 |

原文用 `DCGM_FI_PROF_GR_ENGINE_ACTIVE` 表示引擎活跃时间比例；平台的 `DCGM_FI_DEV_GPU_UTIL` 是另一指标，量纲和采样机制不能直接混用。上述组合是定位线索，不足以唯一证明 NCCL Hang，更不能仅凭异常形状定位根因 Rank。

### 3.2 采样、事件与告警设置（p.2–4、6、14）

| 项目 | 原文给出的设置/判据 | 落地时必须保留的条件 |
|---|---|---|
| 日志停更 | 超过 5 分钟告警 | 区分初始化、长 step、checkpoint 和日志缓冲；优先采用进度心跳而非任意日志 |
| DCGM 采样 | 常见 10 秒；不是要求统一设置为 10 秒 | 微秒/毫秒通信及瞬时 OOM 可能漏采；本平台实际 scrape 周期未查 |
| 累计计数 | 对 PFC、ECN、CNP、CRC 等看 increase/rate | 先确认 counter 类型和重置；XID_ERRORS 是错误码，不能直接 rate |
| SM Clock | p.4：降到基线一半为严重；p.14：偏离基线超过 10% 检查 | 同机型、相似负载/功率策略比较，空闲低频不能当故障；原文未给 for 时间 |
| ECC 复发 | p.6：同卡一周两次摘除/报修 | 按 UUID 和具体错误记录聚合；p.14 对 48 类立即摘卡，与正文单发观察口径不完全一致 |
| Lemon 节点 | 按最近 7 天任务失败次数排名，头部单独诊断 | 需任务—节点关联及失败归因；次数受任务量/运行时长影响，不能直接用次数判坏 |
| GPU 分配率 | 已分配/总 GPU 超过 85% 关注 | 调度资源口径，不是 GPU_UTIL |
| 有效算力比 | MFU 均值/目标 MFU 低于 80% 告警 | 相同模型、精度和 FLOPs 口径；不是绝对 MFU 小于 80% |
| 节点可用率 | 可调度节点/总节点低于 95% 关注 | 与资源管理/调度状态对齐 |
| RDMA 重传 | 作者建议增量长期为 0 | 表中虽称“重传率”，实际写的是计数增量；需补窗口、归一化及正常基线 |
| CNP Slow Restart | 持续增长告警 | 原文未给持续窗口或增量阈值，需核实网卡字段定义 |
| 存储网水位 | 利用率超过 70% 关注 | 预留 checkpoint 突发余量，不将平均值作为峰值保证 |

**原文没有给出完整 Prometheus rule YAML、评估周期、for 持续时间、告警分级/路由或自动隔离规则。以上是作者建议，非本平台已生效配置。**

## 4. 故障五分类：现象、定位与处理方式

| 类别 | 典型现象/细分 | 定位证据与命令 | 原文处理方向 | 平台对应与补充 |
|---|---|---|---|---|
| ① 硬件异常（p.5–7） | Xid、掉卡、PCIe 降速、GPU 降频、频繁异常节点 | dmesg、nvidia-smi -q、lspci；频率/链路宽度基线、7 天失败记录 | 按 Xid 分类复位或摘除报修；供电/散热/链路检查；筛出 Lemon 节点 | XID、ECC、重映射、SM_CLOCK、LINK_WIDTH 和健康检查可辅助；需日志与事件计数确认 |
| ② 通信故障（p.7） | NCCL Hang/Timeout、collective 不匹配、链路抖动、初始化卡住、端口冲突/启动不同步 | 跨 Worker 对齐 OpType、SeqNum、NumelIn/Out；rdma stat、port error/active、Fabric Manager 状态 | 修复 collective 分叉；修复网络；以 Ring 做对照，确认 FM 异常后维护；排查 MASTER_PORT 冲突、对齐启动时间 | nvlink_status、fabric_manager、ib/roce 检查只能辅助，最终需要 Rank 级日志与健康语义 |
| ③ 性能瓶颈（p.7–8） | 确定性降速、慢节点、运行中逐渐变慢、周期性 GC 抖动 | 同配置跨节点指标、SM Clock、send/recv 耗时尾部、同任务多次运行 | 处理降频/降速；尾部节点单独基准；Megatron 主动协调 GC；排除存储/数据加载 | 可用 GPU/SM/Tensor/DRAM/通信指标初筛，需 step/collective 时间和 CPU 数据归因 |
| ④ 任务调度与资源利用（p.8、13） | 8 卡任务跨机导致 TP 变慢、小任务碎片、GPU 越权占用 | K8s Event、分配记录、GPU 进程/显存分布、拓扑 | 大任务整节点与拓扑约束，小任务按卡；设置可见设备，防止越界 | pod/container/UUID 标签可关联，但可见性环境变量本身不是完整隔离边界 |
| ⑤ OOM（p.8–9） | 共享内存不足、GPU 自身超量/抢占/初始化/碎片、NCCL 分配失败、Host OOM | 用户错误日志优先；dmesg 查 Host OOM；/dev/shm、容器限制和显存进程 | 扩充合理共享内存；核查资源占用、checkpoint 加载；动态 shape 碎片可试 expandable_segments | FB_* 看水位，但 10 秒样本不能排除瞬时 OOM；需 OOMKilled/cgroup/训练日志 |

### 4.1 Xid 速查：忠实保留原文，同时标明疑点（p.6，表 4）

| Xid | 原文归类/表现 | 原文处置 | 本次解读限制 |
|---|---|---|---|
| 31 | Memory Page Fault，MMU Fault、illegal memory access | 主要查业务代码，换卡复现以区分硬件/驱动 | 不能仅凭 31 排除硬件/驱动 |
| 48 / 63 / 94 | 合并称“不可纠正 ECC”，举 Row Remapper 日志 | 终止进程、复位；复发报修 | 原文合并不精确：63 涉及 ECC 页退休/行重映射记录，94 涉及 contained ECC；应按当前 NVIDIA Xid 定义及恢复动作区分 |
| 62 / 63 | 又合并称 GPU 内部错误 | 复位，频繁报修 | 63 在原表重复归类，不适合作为平台判定映射表 |
| 74 | NVLink 相关错误 | 查 NVLink/NVSwitch，常需整机维护 | 需定位链路与对端，维护范围取决于拓扑 |
| 79 | GPU fallen off bus | 原文要求停卡报修，不复位重试 | 掉卡是症状；不能仅凭编号证明 GPU 器件本体损坏，需查 PCIe/供电/平台日志 |
| 109 / 119 / 120 | 合并称 GSP RPC Timeout/GSP Error | 原文建议可考虑关闭 GSP | 109 对应上下文切换超时，119/120 才是 GSP RPC 相关；不应统一通过关闭 GSP 处理，需核对驱动和机型支持 |

该表的右栏是独立技术判断，不声称已完成现网驱动对应官方文档核验。任何 GPU reset、FM 重启、GSP 配置修改均可能影响同节点作业，不能由一条 Xid 自动触发。

### 4.2 通信故障细分路径（p.7）

1. **collective 操作不匹配**：对齐所有 Rank 的 OpType/SeqNum/张量大小；先找最早失败或分叉者，再修复业务控制流。超时是结果，不一定是网络根因。
2. **物理链路问题**：对齐 Link down/up 与 NCCL port error/active；抖动可能被重试掩盖，要保留事件。
3. **NVSwitch/Fabric Manager 初始化问题**：查看服务、驱动和拓扑状态，Ring 仅作对照实验；维护 FM 前处理正在运行的任务。
4. **启动基础设施问题**：MASTER_PORT 冲突与 Store 建连超时分别处理；在 torchrun 前记录 Rank/主机时间戳，区分启动未到齐与运行期 Hang。
5. **超时设置**：原文举 30 分钟 collective、300 秒 Store 建连以及 60000ms 日志样例。这些属于不同层级，不是本平台默认值；必须查 PyTorch/NCCL 版本和调用参数。

### 4.3 OOM 细分（p.8）

| 子型 | 原文日志/证据 | 处理方向 |
|---|---|---|
| Shared Memory 不足 | Bus error: nonexistent physical address | 查 /dev/shm、DataLoader 多进程与 Pod 共享内存配置 |
| GPU 自身超量 | CUDA out of memory、Tried to allocate、进程已用 GiB | 查 batch/序列长度/激活/模型状态及分配峰值 |
| 他任务占用 | 刚启动显存异常偏高、进程占用不符 | 核对 GPU 分配和设备隔离，消除非预期占用 |
| cuDNN lazy init | CUDNN_STATUS_NOT_INITIALIZED | 原文指出可能因显存不足；仍需排除版本/驱动/初始化错误，不能当 OOM 唯一证据 |
| NCCL OOM | NCCL WARN CUDA failure 2 'out of memory' | 查通信缓冲与同期显存压力 |
| Host OOM | dmesg OOM、进程被杀；Master 全量加载/保存 checkpoint | 查 cgroup/主机上限和峰值，评估分片加载/保存 |
| 显存碎片 | 动态 shape 频繁分配释放 | 原文建议 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True；先验证版本、兼容性及分配性能 |

## 5. RoCE 网络三类典型故障与处置（p.9–11）

| 故障 | 判据 | 定位 | 原文处理方法及边界 |
|---|---|---|---|
| PFC 风暴 | 接入与上行 PFC 都暴涨、反压逐跳扩散，SSH/监控也卡 | 比较不同端口/优先级；看 headroom、incast、死锁检测 | 收紧 no-drop 优先级到 RoCE 数据队列、核实 headroom 和距离、启用死锁检测；CNP 通道避免被暂停。临时关闭 PFC 仅为原文极端止血方案，会引入丢包，不能直接照做 |
| ECN 门限过高 | 队列高、ECN 标记少、吞吐低 | 队列深度+标记+丢包联合看 | 按带宽/时延/硬件 buffer 重新校准或用动态门限 |
| ECN 门限过低 | 标记率高、吞吐低，但 PFC/丢包干净 | 排除误标记造成无谓降速 | 校准门限；原文“200GE、100KB、利用率六成”为示例，不是通用阈值 |
| QoS 映射错误 | 无损队列报文为 0，默认队列增长 | 查交换机 trust dscp 与主机 ToS/DSCP | 对齐主机与交换机的 DSCP→优先级映射 |
| 无声丢包 | 队列丢弃干净，但 CNP Slow Restart/RDMA 重传增长 | CRC/对齐错误→DDM 光功率/温度→端口翻转 | 查模块老化、污染、弯折、跳线、高温；必要时更换模块/光纤并复测 |

原文 BDP 示例：100Gb/s × 10μs = 125KB，200Gb/s 同时延约 250KB。算术可作数量级参考，**不能直接视为 headroom 的完整配置公式**；还要核实 PFC 反应时间、线缆传播、MTU、硬件 buffer 架构及厂家方案。

## 6. 调优三板斧与验收（p.11–13）

| 板斧 | 原文动作 | 原文验收/收益 | 适配限制 |
|---|---|---|---|
| 集合通信 | DSCP 对齐、GID 选择、超时重试、拓扑、版本统一 | ib_write_bw；all_reduce_perf -b 8M -e 4G -f 2 -g 1；看带宽及抖动 | 用现网节点数/进程启动方式补完整测试；Ring 用于对照，不保证最优 |
| 数据加载与存储 | 存储与训练网络分离；checkpoint 分片/异步；扩大 /dev/shm | 消除周期性掉速和存储写入反压 | 原文“训练网 PFC 为 0”不能直接成为所有负载的验收标准，应区分正常反压与存储诱发退化 |
| 任务排布 | 大任务整节点、TP 尽量机内、rail-optimized；小任务按卡 | 同任务多次运行 MFU/吞吐方差 | TP≤8 来自文中 8 卡主机假设，不是所有拓扑通用上限；约束与碎片需权衡 |

原文给出的 NCCL 参数是示例起点，**没有在本平台执行或验证**：

| 参数/命令 | 原文值 | 说明 |
|---|---|---|
| NCCL_IB_TC | 106 | 106 = (26 << 2) + 2，对应 DSCP 26；交换机映射到优先级 3 是文中环境 |
| NCCL_IB_GID_INDEX | 3 | 按 show_gids 选择 RoCEv2；新版本可能自动选择，不应固定抄 3 |
| NCCL_IB_TIMEOUT | 22 | RDMA 超时参数，不是 22 秒，也不是 PyTorch collective timeout |
| NCCL_IB_RETRY_CNT | 7 | 重试设置需按驱动/NCCL 与网络实测 |
| NCCL_ALGO | Ring | 排查 NVLS/FM 时作对照 |
| NCCL_PROFILER_PLUGIN_ENABLE | 1 | 原文写法；参数名、插件安装与版本支持尚未核验，不当作可直接执行配置 |

原文称 NCCL 2.20.x 的 Message truncated、部分 invalid device context 问题在 2.21+ 修复（p.11），本次未核对具体 release note，不将“统一升级 2.21”作为通用解决方案。原文 p.7 的 `NCCL_ALGO=NVSL` 与 NVLS 拼写不一致，应核对官方支持列表。

Checkpoint 示例（p.12）：70B 参数 bf16 权重约 140GB，按文中 12B/参数附加状态约 840GB，总量近 1TB；2×100Gb/s 理想吞吐 25GB/s，集中写约 40s；128 分片每份约 8GB，理想每节点耗时约 0.3–0.4s。这里假定状态口径与分片布局，实际仍受聚合存储吞吐、持久化、并发与协议开销限制。文中 30 分钟/5 分钟 checkpoint 间隔是经验场景，需按保存成本与故障率权衡。

## 7. 日常巡检与故障闭环（p.14–15）

| 频率 | 检查内容 | 异常后的动作 |
|---|---|---|
| 每日 | 24h Xid、SM Clock 基线、网卡速率、PFC/ECN/headroom、CRC/光功率、近 7 天失败排名 | 按前述类别留证、定位、摘除观察或报修；避免仅凭总数归因 |
| 每周 | GPU/LLDP 拓扑、点对点/集合通信带宽、全节点基准尾部、驱动/固件/OFED/NCCL 版本 | 查变更、隔离诊断慢节点、规划一致性维护窗口 |
| 交付与每次硬件/网络变更前后 | ib_write_bw、all_reduce_perf、单节点训练 MFU；拓扑与配置快照 | 对比回归并保留时间、版本、配置、原始结果 |

## 8. 个人评述与对 AOM/ltp_ha 的启发

1. **最值得复用的是证据分层和基线，而非硬编码阈值。** 已有 51 个 DCGM 指标足以搭建 GPU 面初筛；任务进度、网络/链路原始计数仍需单独发现与验证。
2. **补齐任务进度比继续堆利用率更关键。** 需要 Rank/step/阶段/last-progress、checkpoint 状态及最早失败日志；高 GPU_UTIL 不证明有有效计算。
3. **健康状态必须核实语义。** node_health_check_state 的 pass/fail/unknown/skipped 需先确认 one-hot 值；存在 fail 时序不等于故障激活，unknown/skipped 不算通过。
4. **不能把 Xid 代码变成 counter。** XID_ERRORS 是最近错误码；频次要用经过验证的自定义 counter 或日志事件，带 UUID、时间和代码去重。
5. **文章存在经验性绝对表述。** MFU 不能无条件跨模型公平比较；Util/SM 组合不唯一对应 Hang；Tensor>50% 不证明无优化空间；频率/PCIe 问题也并非只能用基线发现。
6. **不要把缺少本次发现结果等同平台缺失。** 本次指标正则未穷举任务、网卡、交换机及调度指标；下一步应按 exporter/集群查名称、HELP/TYPE、样本有效性和真实告警规则。
7. **把诊断和恢复解耦。** 软件 collective 分叉、初始化依赖慢、Host OOM 与硬件坏卡应采用不同恢复策略；先分类再决定是否重启任务、换节点或报修。
