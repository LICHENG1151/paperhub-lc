# MegaScale：万卡训练扩展与故障恢复

返回 [本篇导航](./README.md)。原文首发 2024-02-23，下载及分析日期为 2026-10-28。引用页码对应随档 arXiv v1 PDF；本文没有复现实验，也没有验证 veScale 当前代码是否覆盖论文全部生产能力。

## 1. 一句话总结

MegaScale 将算法与系统协同优化、全栈可观测性和故障恢复闭环结合，使万卡任务既跑得快，也能在数周内不断恢复并维持有效训练时间；对 ltp_ha 最有借鉴价值的是“检测—全局停止—诊断—隔离换机—恢复”和跨 Rank 的因果定位，而不只是 GPU 指标告警。

## 2. 背景与问题

单个万卡训练作业持续数周，任一节点故障可能使全局重启，任一慢 Rank 可能拖慢整个同步组。论文将问题分为：

- **训练效率**：并行通信、算子、数据加载、初始化和网络均可能占用关键路径。
- **训练稳定性**：故障、隐性慢节点和软件抖动持续侵蚀有效训练时间；单机基准或 GPU 利用率未必暴露问题。

作者单位为字节跳动与北京大学。系统基于 Megatron-LM 构建，论文实验基线 commit 为 `285068c8`（§6.1，p.9）。不能把本文相对收益理解为对当前 Megatron 最新版本的收益。

## 3. 核心思想与实现

### 3.1 训练效率：优化真正阻塞后继计算的路径（§3，p.3–6）

| 层次 | 做法 | 为什么有效/边界 |
|---|---|---|
| 模型与优化器 | 并行 Transformer block（Attention、MLP 同输入并行）、滑窗注意力 SWA、LAMB 扩大 batch | 不仅改系统，还改变模型/优化配置；收益不是完全相同算法下的实现加速 |
| DP | 按 model chunk 预取参数 all-gather，反向后尽早 reduce-scatter；第一次 AG 与数据加载重叠 | 利用计算依赖调通信优先级，仍需处理首尾无法完全隐藏的通信 |
| PP | interleaved 1F1B；拆开耦合的 send/recv，分别异步提交 | 避免不必要依赖阻塞 warm-up 与 steady phase |
| TP/SP | 将 AG/RS 融入 FFN Linear；GEMM 分块后与通信流水重叠 | FFN 的较大计算量提供隐藏通信的窗口 |
| 算子 | FlashAttention-2、LayerNorm/GeLU kernel fusion | 降低 kernel launch 与显存访存开销 |
| 数据 | 下一步预处理与当前梯度同步重叠；同机一个 loader 读共享内存，各 GPU 再复制 | 假定同机属于同 TP 组且输入相同，不能无条件推广到混合任务 |
| 通信组初始化 | Redis 替换当时 TCPStore 阻塞路径；调整初始化顺序，减少全局 barrier | 2048 GPU 从 1047s→361s→小于 5s，万卡小于 30s；这是当时实现，不是现代 TCPStore 固有上限 |
| 网络 | 三层 Clos、1:1 上下行；8×200G 多 rail；减少 ECMP 冲突；RTT+ECN 拥塞控制；重传调优 | 软件放置和物理网络共同设计，论文未给可直接复制的完整配置 |

并行 block 将串行 `x + MLP(LN(x + Attention(LN(x))))` 改为 `x + MLP(LN(x)) + Attention(LN(x))`。这类改动需重新验证收敛与模型质量，不能作为透明运行时补丁。

### 3.2 容错流程：控制面协调全局恢复（§4.1，Figure 5，p.6）

```text
Driver 向 Kubernetes 申请资源
  → 每节点 Executor 启动 GPU workers + 心跳 daemon
  → Driver 发现进程异常 / 心跳超时 / RDMA 流量完全停止
  → 停止各 Executor 上的训练，执行诊断
  → 汇总坏节点 IP 与 Pod，交给 Kubernetes 驱逐并等量补充健康节点
  → 新节点通过诊断
  → 从最新 checkpoint 恢复
```

另有人工驱逐入口，用来处理自检无法捕获的间歇故障。论文强调自动化闭环，但不是不停训原地修复，也不是已证明支持任意缩容后的并行度重映射；其主流程是等量替换资源后恢复。

### 3.3 检测与监控设置（§4.2，p.7）

| 信号 | 论文采集内容 | 论文动作 | 未披露/需要补齐的设置 |
|---|---|---|---|
| Executor 心跳 | IP、Pod、硬件信息、训练进程状态 | 状态异常或预定义窗口未收到心跳，触发恢复 | 具体心跳周期、超时阈值、去抖和控制面故障隔离未给出 |
| 日志 | stdout/stderr 聚合、过滤、实时关键词分析 | 报告诊断信息，结合进程状态处理 | 错误码规则、误报率和优先级未量化 |
| RDMA 流量 | 利用率与逐 step 周期模式 | 明显下降/异常波动告警人工调查；流量完全停止自动恢复 | 未给流量窗口、训练阶段豁免、零流量判定阈值 |
| 秒级监控 | 健康、ECN/PFC/QoS、NIC 与链路抖动 | 排除常见配置/健康问题 | 没有统一 exporter schema 或规则文件 |
| 毫秒级监控 | 拥塞及 DP/PP 传输是否接近带宽上限 | 支持性能诊断 | 毫秒监控不等于把所有 Prometheus scrape 改成 1ms |
| CUDA Event | 每 Rank 的前向/反向/通信等关键代码段时延 | 常驻生产；跨 step 聚合热图和跨 Rank 时间线 | 只称开销可忽略，未给数值、精确跨设备时钟校准方法 |

**最重要的边界**：异常降速告警与完全无进展恢复是两档处理。落地前必须区分训练、初始化、checkpoint 和合法等待阶段；直接“RDMA=0 就重启”可能误判。

### 3.4 诊断测试：不是仅靠静态健康检查（§4.3，p.7）

| 测试 | 范围 | 可发现问题 |
|---|---|---|
| RNIC loopback | RNIC 到主机内各内存节点/GPU endpoint，full mesh | PCIe 路径带宽退化、配置异常 |
| RNIC-to-RNIC | 同机不同 RNIC 间连接及带宽 | 网卡能力、路由配置 |
| 单机 NCCL all-to-all | 本机所有 GPU | 机内 GPU 通信异常 |
| 跨机 NCCL all-reduce | 同 ToR 下相邻机器 | 机间通信异常 |

测试时长与误判率存在权衡，论文没有给各项阈值、样本次数、机型基线或精确故障覆盖率。训练停止后运行诊断与正常运行期间采集监控是两条路径。

### 3.5 Checkpoint：缩短阻塞，同时降低恢复读取风暴（§4.4，p.7–8）

**保存两阶段**：GPU 状态先写入 host pinned memory，经序列化优化后阻塞降至数秒；后台进程异步写 HDFS。**恢复**：共享相同状态的 worker 由一个代表读取，再广播，减少重复 HDFS 请求。

需要避免三个误读：

1. GPU→主机数秒是前台暂停，不是 HDFS 持久化完成时间。
2. 主机内存快照与持久 checkpoint 的故障域不同；节点故障时尚未持久化的状态可能丢失。论文未完整描述 manifest 提交、一致性协议和后台写失败处理。
3. 只对确实相同的状态做一次读取再广播；ZeRO 的不同分片不能被当成相同数据。不能概括为“DP 全组只读一份所有优化器状态”。

### 3.6 隐性故障定位：先看依赖，再看谁没报告（§5，p.8–9）

CUDA Event 数据写本地逐行日志，由独立 streamer 送 Kafka，再入远程分析数据库。这样将分析链路与训练关键路径分开。

- **热图**：按 Rank/机器汇总前后向耗时，找到约 0.5% 显著慢节点；单 GPU GEMM 微基准没有发现明显差异。
- **分布式时间线**：按 TP/PP/DP 通信组聚合，显示流水线气泡、同步等待与操作依赖。
- **3D 逻辑拓扑**：发生通信超时时，各 worker 输出当前操作；依赖坏节点的 worker 会记录等待操作，而真正整机 Hang 的节点可能完全没有输出。利用依赖关系与缺失报告定位后人工隔离。

“没有日志”在论文中需结合拓扑和其他节点报告使用，不是单独证明坏节点。日志链路断开、机器重启和控制面失联也可能造成缺失。

## 4. 实验与结果：区分效率、收敛和可靠性

### 4.1 训练扩展（§6.1，Table 1/2、Figure 9，p.9–10）

硬件为 NVIDIA Ampere 集群。序列长 2048、词表 64000；175B 为 96 层、hidden 12288、128 heads、TP=8、PP=8、6 个 interleaving stages；530B 为 105 层、hidden 20480、160 heads、TP=8、PP=35、3 个 interleaving stages。

| 模型/设置 | Megatron-LM | MegaScale | 解释 |
|---|---|---|---|
| 175B、12288 GPU、batch 6144，MFU | 41.2% | 55.2% | +14.0 个百分点，约 1.34×；不是 +14% 相对提升 |
| 同配置 step time | 8.57s | 6.34s | 约 26% 缩短 |
| 同配置吞吐 | 1466.8k tokens/s | 1984.0k tokens/s | 论文表中直接报告值 |
| 175B、3072→12288 GPU，batch 6144 | MFU 48.7%→41.2% | 59.1%→55.2% | 固定 batch 强扩展；计算/通信比随规模变化 |
| 530B、2240→4480→11200 GPU | 49.2%→48.8%→48.2% | 54.3%→54.1%→54.3% | batch 随 GPU 增长，为弱扩展；最大差值 6.1 个百分点 |

Table 2 另有 256–1024 GPU、batch 768 的小规模组，不能将其与 batch 6144 组当成一条全范围固定 batch 曲线。论文表中 300B tokens 的训练天数按该吞吐口径报告，不等同真实数周生产运行的有效时长。MFU 不等于 DCGM GPU_UTIL。

### 4.2 消融（Table 3，p.11）

175B、256 GPU，基线 batch 256，最后一项 LAMB 将 batch 扩至 768。网络优化对基线与 MegaScale 均开启。

| 累积增加项 | MFU | 相比上一步增量 |
|---|---:|---:|
| 基线 | 47.7% | — |
| 并行 Transformer block | 52.3% | +4.6 pp |
| SWA | 53.3% | +1.0 pp |
| TP overlap | 55.5% | +2.2 pp |
| PP overlap | 58.0% | +2.5 pp |
| DP overlap | 59.5% | +1.5 pp |
| 高效算子 | 61.2% | +1.7 pp |
| 数据及其他优化 | 62.3% | +1.1 pp |
| LAMB，batch×3 | 65.3% | +3.0 pp |

累计 +17.6 个百分点；这是顺序叠加消融，不是每项独立收益。LAMB 收敛微实验为 batch×4，而这里是 ×3，需区分。也不能将 17.6 pp 全归因于通信或容错。

### 4.3 收敛与生产可靠性（§6.2–6.3，Figure 10/11，p.11–12）

- **收敛微实验**：13B 模型，PTB/SWA 在超过 100B tokens 上与基线 loss 接近；LAMB 以 Adam 4 倍 batch 训练约 250B tokens 后 loss 接近。这不等于所有大模型下游任务质量均已验证。
- **生产作业**：数千亿参数量级的私有模型（原文 hundreds of billions），数万亿 tokens，万卡运行数周，经历超过 100 次重启；归一化 loss 继续下降。
- **自动化覆盖**：作者称超过 90% 的软硬件异常可自动检测、定位并恢复，剩余借助诊断工具处理；没有逐故障类别的混淆矩阵。
- **时间口径**：故障检测加诊断平均小于 10 分钟；另称从最近 checkpoint 可在 15 分钟内追平崩溃前进度。论文未给精确计时起止分解，不能把两数随意相加或宣称所有故障端到端恢复小于 15 分钟。
- **有效训练时间比例**：超过 90%，定义为迭代数×迭代训练时间/总训练时间；不是 90% MFU，也不是零重算或零数据丢失。

## 5. 论文实际发现的故障与处理

| 类型 | 证据链 | 处理 | 来源 |
|---|---|---|---|
| 显式异常、心跳丢失 | 进程状态、日志、daemon 心跳；例 CUDA error、segfault | 停训诊断、换机、checkpoint 恢复 | §4、§6.3 |
| 隐性计算慢节点 | 相同前向耗时约慢 10%，跨实验稳定出现 | 隔离慢机器，作者报告约 +0.7% MFU（绝对/相对口径原文未明确） | p.12 |
| MFU 随时间下降 | 前后向/optimizer 计算耗时稳定；最后 DP reduce-scatter 变长；网络带宽稳定；两 Rank 复现发现 launch time 交替错位 | 追踪关键路径软件扰动，修改/移除不规则 GC 和某些 PyTorch 操作引起的抖动 | p.12 |
| 间歇 GPU Hang，常规自检漏掉 | 下游大量超时但部分根节点无退出日志；依赖拓扑定位 | 人工隔离、标记维修 | §5.2，p.9 |
| 网卡 link flapping | down/up 间隔数秒、期间在途报文丢失 | 显式设置足够的超时容忍短暂抖动，调重传并启用适配特性；改善 NIC/AOC/交换机信号质量 | §3.6、§6.3 |

论文中的“GC 导致偏斜”是观测链闭环；并没有给出“统一开启 Megatron 某 GC 参数即可解决所有慢节点”的结论。链路抖动案例还明确说明超时过短会过早失败，不能把容错优化理解为一律缩短超时。

## 6. 个人评述与对 ltp_ha / AOM 的启发

### 6.1 最值得迁移的能力

| 论文能力 | 当前 AOM 证据可辅助什么 | 需要另外验证/建设什么（建议，不代表当前实现） |
|---|---|---|
| 资源身份与故障关联 | cluster/node/gpu/UUID/pod 等标签 | job、Rank、TP/PP/DP 坐标、执行轮次和节点替换历史 |
| 基础硬件筛查 | SM_CLOCK、ECC/XID、PCIe/NVLink、健康检查名称 | 检查状态编码、真实错误事件与有效采样；counter 与错误码区分 |
| 无进展判定 | GPU/通信指标可提供旁证 | 独立进度心跳、last-step、阶段、checkpoint 状态，避免初始化/存储阶段误判 |
| 慢 Rank 定位 | GPU 活跃度、频率、温度/功耗横向对比 | CUDA Event 代码段计时、collective launch/finish、跨 Rank 依赖与时间线 |
| 故障后诊断 | node_health_check_state 可作为信号入口 | 静态健康与负载测试分层，设置诊断预算、基线与结果期限 |
| 节点恢复准入 | 健康状态可参与评估 | 隔离原因、维修证据、复测和重新准入，不能一过健康检查就忘记历史 |
| Checkpoint 恢复 | 原有 DCGM 不足以判断 | 持久化完成标记、一致性、失败回退、分片映射、加载量与恢复耗时 |

这些是论文映射建议，本次没有审计 ltp_ha 代码，不能据此判断项目是否已经实现或缺少对应功能。

### 6.2 关键判断

1. **硬故障和性能退化应分开闭环。** 确定性异常走自动恢复；慢节点及疑难抖动走证据聚合与受控隔离，避免正常节点被误摘。
2. **AOM 指标是证据的一层。** 论文真正定位隐性慢节点的是 Rank 级执行时间和依赖关系；现有 51 个 DCGM 指标无法替代训练内观测。
3. **恢复预算应拆开衡量。** 检测、停止、诊断、资源替换、初始化、读 checkpoint、重算追平分别计时；只统计“进程启动成功”会隐藏大量损失。
4. **异步 checkpoint 不等于已持久化。** 需要 committed checkpoint 状态、失败重试和恢复选点策略；论文给出方向，未给完整协议。
5. **不要直接照搬 2024 配置。** 当前 PyTorch/NCCL 的初始化行为、硬件、网络和 exporter 语义不同；Redis 替换、LAMB/SWA、重传策略均需独立评估。

## 7. 结论与局限

论文证明了生产环境中的全栈优化与恢复闭环可以同时提高单步效率和长期有效训练时间。它对系统工程很有价值，但不是可直接部署的完整运行手册：缺少详细阈值、故障覆盖率与误报率、控制面自身容错、checkpoint 原子提交协议和大规模独立复现材料。

效率实验使用旧 Megatron 基线，且改变了算法结构；可靠性来自单个披露有限的私有生产案例。代码脚注指向 veScale，只能说明作者提供的开源入口，不证明论文全部诊断/网络/容错系统已经公开。
