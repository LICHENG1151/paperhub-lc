# Mara Chain：失败候选驱动的 AI 系统自进化

[本篇导航](README.md) · [本月索引](../00-README.md) · [原文 PDF](2609.35855v1.pdf)

## 一句话总结

冻结模型权重，把提示词、Skill、脚本、Harness 与流水线代码视为可编辑产物；保留被拒绝候选及其失败证据，沿有限深度的修复链继续改进，再用验证分数筛选候选。核心价值是累积修复进展，实验对未知任务泛化的支持则有限。

## 来源与阅读范围

- 论文发表于 **2026-09-25**；2026-10-29 查询 arXiv 页面所见版本为 **v1**，原文 32 页。
- 作者单位：Ant Group（Yubin Lyu、Weixing Mei、Yinan Wu）、Beijing Intelligent Game and Decision Lab（Fu Li）、Beijing Defense Innovation Institute（Jiawei Fei、Yang Zhao）。属于联合研究预印本。
- 本文依据论文正文、算法与实验附录，核对 PDF 第 6、7、24 页的表格和实验协议；另读取官方 AntOmniEvo README。没有运行实验，也没有完成实现源码审计。
- 与此前的 MegaScale 主题区分：这里的 failure 是任务执行/候选优化失败；论文未研究 GPU 硬件故障检测、训练 checkpoint 恢复或 A100/H100 的 MFU。

## 背景与问题

传统 propose–evaluate–select 循环只保留超过父代分数的候选。复杂任务往往需要连续修复：先修入口、再修逻辑、再修性能，任何一个中间版本都可能仍然失败。立即丢弃会同时丢失局部有效修改与诊断证据，后续提案容易重复走弯路。

Mara Chain 把“未达接受门槛”和“没有研究价值”分开处理：失败版本不进入正式候选池，但可以作为后续链节点的起点。适用前提是系统能表示成文件目录，并且存在可重复、成本可承担的评价函数。

## 核心思想

### 1. 外层种群搜索 + 内层连续修复

1. 从候选池选父代：偏向在某些任务维度上领先的候选，而非只取平均分最高者。
2. 在训练 minibatch 上评估父代，提出并运行子代。
3. 若子代超过相对父代的接受门槛，进入验证阶段；否则保留子代，启动 Mara Chain。
4. 后继节点继承最近失败版本，结合跨版本证据继续修复。链内使用同一个 minibatch，以便比较差异。
5. 达标则退出链并验证；到达深度上限仍不达标则不晋级，已花费的计算仍计入成本。
6. 根据验证集各任务分数组成的向量做 Pareto 过滤，再保留平均分最高的 Top-N，限制候选池规模。

相同验证向量按文中规则偏向更新/更深的候选。Top-N 截断仍可能丢掉某些局部专长，并非保存完整 Pareto 前沿。默认 N=3、链深度 d=5，但各实验存在覆盖配置，不能一概套用。

### 2. 记住的不是一句“经验教训”

链上下文包括：产物文件、父子谱系、逐任务得分、相对根节点和前一节点的差值、带候选归属的 changelog、历史 RunAnalysis、原始运行轨迹和仍未满足的条件。

分析阶段读取运行证据；修改阶段主要消费压缩后的分析与改动历史。将这两步分开能减少长日志直接挤占编辑上下文，但分析压缩本身也可能丢信息。论文设计中验证运行与 proposer 隔离；这不等于所有实验最终测试都与选择过程独立。

### 3. 提高修复的执行可靠性

论文案例体现了从自然语言提醒到可执行脚本、再到运行时扩展的演进。比如规则本来正确却始终没被执行，继续追加提醒可能无效，应检查调用入口，必要时改成必经执行逻辑。脚本或扩展只有被调用才有价值，形式升级不自动保证正确。

## 实现细节与诊断分类

AntOmniEvo 将 System、Evaluator、数据、Optimizer、Proposer、Evolution Algorithm、CandidateStore 分离。用户提供可调文件 schema、初始产物、运行方式、评分方式和数据；框架调度、持久化、限预算和筛选，coding agent 编辑文件，最后输出可审阅的文件目录。

附录 D（PDF pp.22–23）要求跨尝试诊断结合五种操作：沿差值追溯证据、提取成功执行、发现来回退化、识别同配置随机差异、用运行片段佐证判断。九类诊断尤其值得复用：

| 类别 | 含义 | 建议修复动作 |
|---|---|---|
| A never-triggered | 新增内容根本没有触达 | 修触发入口或移动到必经路径 |
| B content-wrong | 执行了错误内容 | 删除或替换 |
| C vague | 原则正确但不可执行 | 写成 WHEN / DO / VERIFY 步骤 |
| D conflict | 被其他内容覆盖 | 找出冲突来源并消解 |
| E root-cause-irrelevant | 改动与真正根因无关 | 重新定位根因 |
| F direction-exhausted | 同一方向反复尝试无收益 | 更换组件或机制 |
| G inconsistent | 同一配置表现不一致 | 检查随机性，强化成功路径 |
| H lost-win | 曾经有效的改动被删掉/覆盖 | 恢复并增加回归保护 |
| I mechanism-too-weak | 内容正确但系统绕过了它 | 提升到可靠的执行机制 |

这九类是 **Agent 产物与行为诊断**，不是 GPU 故障分类。论文倾向 REMOVE/REPLACE 而非无限 ADD，并要求指出责任候选，避免相互打补丁造成规则冲突。

## 实验与结果：数字及其适用边界

### AppWorld：结果较强，但协议记录存在明显缺口

Table 1（p.6）的静态评估覆盖 585 题：Normal 168、Challenge 417。TGC 是任务整体通过率，SGC 要求同一 scenario 中所有任务通过才算该 scenario 成功。

| 配置 | Normal TGC | Normal SGC | Challenge TGC | Challenge SGC |
|---|---:|---:|---:|---:|
| Empty skill | 48.2 | 35.7 | 33.3 | 19.4 |
| SkillOpt-Lite | 70.8 | 51.8 | 68.3 | 46.0 |
| GEPA | 83.3 | 67.9 | 69.3 | 44.6 |
| ACE | 83.9 | 69.6 | 74.1 | 55.4 |
| Mara Chain | 89.9 | 83.9 | 76.7 | 59.0 |

单位为 %。Mara 行的 Normal 来自标为 2-slot 的结果，Challenge 来自 1-slot；不是一个配置包揽四列最优。摘要“最高相对提升 20.5%”可对应 Normal SGC 的 83.9 相对 69.6，绝对差为 14.3 个百分点。

正文报告达到验证分数 0.8 时需要 3,280 次 rollout，GEPA 为 9,514 次，减少 65.5%；附录 F 报告有效时间 11.9h 对 35.8h。这些是论文报告的优化轨迹，不能当作已被独立复现的成本结论。

**关键证据限制（附录 E，p.24）：**

- 描述的训练池是 147 题；验证集从最终测试池抽取 200 题，最终 585 题包含这 200 题。因此最终成绩不是完全独立的 held-out 测试。
- 同页又明确说没有 optimizer manifests；优化运行设置、模型分配、minibatch、验证过程、预算和基线启动参数不可得，1-slot/2-slot 的历史含义也无记录。
- 附录仅承认静态最终评估记录的证据范围，与正文的优化过程比较存在可追溯性张力。不能把前面的 split 描述当作已验证的完整历史实验配置，更不能据此声称能复现“少 65.5% rollout”。

### TerminalBench 2.1：已见任务的优化能力

| 配置 | 89 题通过率 |
|---|---:|
| Mara Chain | 71.9% |
| 去掉 Mara Chain | 57.3% |
| AHE / Codex harness / Kira base | 51.7% |
| Meta-Harness / OpenCode harness | 49.4% |

Mara 相对 AHE 为 +20.2 个百分点；相对 Meta-Harness 为 +22.5；相对自身无链消融为 +14.6。

所有行均使用冻结的 **GLM-5 system model**。这里的 Codex 是搭配 GLM-5 的 harness 参照，不是 OpenAI 原生模型或官方产品榜单。附录 E 明确：89 题既供优化又供最终评测，没有独立验证/测试集。因此 71.9% 是 in-sample optimized-task rate。

文档化的 Mara 配置为池大小 1、batch=4、最大反思次数 5、预算 100h；proposer 为 GLM-5.1 Pi coding agent。AHE、Meta-Harness 也列了 100h 预算，但运行机制和并发/试验次数不同；AHE 的外部知识获取被关闭。相同 wall-clock 不代表相同 token 或 API 成本。

### MuSiQue 4-hop：最值得关注的泛化证据

300 train / 100 val / 300 test，test 与 val 不重叠（后二者均来自官方 dev 再划分）。指标衡量前十个检索文档，而非最终问答正确率。

| 配置 | 测试 nDCG@10 | 测试 Recall@10 |
|---|---:|---:|
| 手写默认流水线 | 0.301 | 0.329 |
| 自动优化但无 Mara Chain | 0.371 | 0.421 |
| 完整 Mara Chain | 0.405 | 0.460 |

相对手写基线分别 +0.104 / +0.131；相对无链消融才是 +0.034 / +0.039。不能把全部收益都归给失败链。无链与完整配置在表中采用相同 2-slot 预算。

附录给出完整配置：N=3、batch=6、num_proposals=2、反思次数 3、20h wall-clock。演化后的检索流水线加入 GLM-5.2 query rewrite、增加稀疏/稠密召回、双查询与 RRF、图扩展、rerank 等。查询成本与系统复杂度也随之变化，仍需延迟、token 成本和多次重复实验来判断工程性价比。

### 消融不是“加链必然更好”

AppWorld 1-slot 中，Normal TGC 有无链都是 86.9%；Normal SGC 完整版本 75.0%，无链反而 76.8%。Challenge SGC 则为 59.0% 对 51.8%。这支持复杂任务更可能受益，但不能证明所有任务都适合深链。

图 3 消融用的是验证阈值 **0.79**（完整 2,356 次 rollout），正文效率比较用 **0.8**（3,280 次）；两个阈值与实验图不能混用。AppWorld 的消融过程也受到上述历史记录缺失限制。

## 结论与局限

1. **评测独立性不足。** TerminalBench 没有留出集，AppWorld 选择数据与最终测试重叠；MuSiQue 的划分较清楚。
2. **复现材料尚未齐备。** 截至本次访问，官方 README 表示论文实验脚本、演化前后产物和数据还在准备，将另库发布。框架公开不等于整套论文实验已可复现。
3. **同批次反复修复可能过拟合。** 验证筛选能缓解但不能消除，尤其验证集也被反复用于选优时。
4. **随机分数会误导选择。** 单次成功可能是幸运样本；逐任务领先的采样机制也可能让某些候选长期得不到机会。
5. **机制和预算尚需更严格分离。** 有消融不代表所有收益都来自失败记忆；需要等成本重启、只保留文字诊断、只继承文件等对照来分清原因。
6. **理论是有条件陈述。** 附录 C 的结论依赖残差完整可观测、更新不退化、可实现性、每次成功概率的条件下界等假设；论文明确未用实验建立这些假设。不是对任意 AI 系统最终成功的保证。

自适应链深、Mara-tree、跨任务经验库等属于后续方向，不应当作本文已验证能力。

## 个人评述与启发

**我的判断：工程方法值得借鉴，排行榜提升应谨慎解读。** 最有价值的创新在于把失败作为带谱系的工程状态，保住局部有效改动，而不是只多写一段反思。

对于我们已有的 Skill / Agent 工作流，可先借鉴三件事：

- 每次失败保留候选文件、运行日志、明确的未满足条件和已通过项，避免下次修复从空白开始。
- 用 A–I 分类判断是内容错误、未触发、机制太弱还是旧收益丢失，再决定改提示词、脚本或执行入口。
- 给修复链设预算和退出条件；晋级前跑独立回归集，最终测试集不参与任何候选选择。记录成功率之外的时延、API 成本及回归数量。

若将其用于训练运维 Agent，适合先离线优化“日志分类—证据定位—建议动作”的诊断产物。论文并未证明它能安全执行坏节点隔离、重启或集群配置变更；这些动作的正确性还需要另外的环境约束与故障演练。

最低限度的验证方案应比较：单次重提、仅保留诊断文字、继承文件但无历史证据、完整链四组，在相同模型与总预算下，报告独立测试表现、多次运行方差和回归率。这是本人的复现建议，本次未实施。
