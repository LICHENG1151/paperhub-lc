# 2026 · 大规模智能体训练的弹性沙箱基础设施

**状态**：已消化

[返回月索引](../00-README.md)

> 原文：DeepSeek Elastic Compute (DSec): A Sandbox Infrastructure for Effective Agentic Training at Scale，arXiv v1，31 页，首页标注 2026-09-19。本文通读正文并核对关键图表；数值均为作者报告，未部署系统或复现实验。`code` 指论文披露的存储组件，不代表完整 DSec 已开源。

## 1. 一句话总结

DSec 将多种沙箱后端、可组合环境层、3FS 按需镜像读取、内存回收与 CPU 隔离整合成 Agent 训练平台，并把有状态 rollout 移出可抢占的 GPU 任务，使环境能够独立存活、暂停和恢复。它减少环境准备与状态丢失造成的训练浪费，但不是新 RL 算法，也没有承诺训练数值逐位复现。

## 2. 背景与问题（§2–4，pp.4–13）

Agent 训练同时具有突发创建、长期保留状态、CPU 间歇使用和镜像高度多样化的特征：单个任务可请求 32K 沙箱；约 90% 的 container/microVM 平均使用不超过申请 CPU 的 5%，但两类沙箱中位存活时间仍有 17.4、15.5 分钟，p99 均超过 3 小时。CPU 可以超卖，内存、文件修改与后台进程却不能随之消失。

一周活跃环境超过 130 TB；容器镜像的任务内 fanout 中位数只有 3，microVM 为 1。抽样的不同语言环境仅访问镜像数据的 4.2%–13.3%。因此，完整拉取镜像、逐实例解压工具包，以及只靠节点本地缓存，都不适合这种低复用、大工作集负载。

**生产规模与实验规模必须分开。** 单个生产 scale unit 约 160 个 CPU 节点、30K CPU 核、250 TB DRAM，日服务约 300 万沙箱，峰值并发约 38 万、创建速率超过 5,000/s（§2.4）。单节点 3,200 个容器或 800 个 microVM 是观察到的运行点，不是硬上限，也不表示所有实例同时满负载。第 8 节的受控评估另用 10 节点集群。

## 3. 核心思想与实现

### 3.1 多后端与两级准入（§2–3、§7）

`libdsec` 提供统一入口，但调用者仍需选择后端：FnCall 面向短时无状态任务，container 面向代码仓与工具调用，Firecracker microVM 提供更强隔离，完整 QEMU VM 支持完整操作系统及图形任务。统一 SDK 不抹平后端语义差异；FnCall 使用预创建容器，执行后仅 best-effort 清理，不能当作每次全新的强隔离会话。

创建请求经过 IAM 授权、placement engine 选点、apiserver 转发，最终由节点上的 `edge` 做实时容量准入。placement 按能力过滤，用 power-of-k-choices 选较空节点，并在周期性 watcher 快照上叠加本实例尚未反映的新放置。即使全局视图陈旧，edge 仍可拒绝并触发换点。

container/VM 的后续命令经过 `edge → aether → chronus`：aether 管沙箱通信与会话，chronus 对应独立 shell 会话；FnCall 走独立路径。生产中的 FnCall/container 位于 QEMU/libvirt VM 内，不能画成“不可信容器直接共享裸机内核”。apiserver 无逐沙箱执行状态，sandbox ID 编码所属 edge，便于入口横向扩展（图 1，p.6）。

### 3.2 环境组合与按需读取（§5.1、§5.3，pp.14–17）

环境拆为独立版本的 **base image、workspace、toolkit**。启动时在 overlayfs 的只读 lower 层组合，运行写入落到本地 upper 层；既合并目录，又允许工具写自己的安装路径。工具更新只重建对应层，避免跟所有 workspace 组合重建。论文报告修改 dockerd 动态插入 lower 层约 30 行 Go 代码。

容器层采用 EROFS：元数据预取到节点，文件数据保留在 3FS，按访问需求读取，利用 readahead 聚合 I/O。关键是适配 3FS 的“大块高吞吐、小随机 I/O 较弱”特征：**小写留本地、元数据尽量本地、远端数据按需大块读**。

microVM 不完全照搬容器存储：只读基础层/toolkit 使用 EROFS，需要可写 ext4 或 Docker-in-VM 的磁盘走 `OverlayBD → ublk`，以 256 KiB 块读取并使用本地二级缓存。这是兼容性取舍；其 ext4 元数据仍可能触发远端 I/O。

### 3.3 内存与 CPU QoS（§5.2、§7）

- **virtio-pmem + DAX**：让 guest 共享 host 后备页，减少重复 page cache，适合只读层。但 guest 的 `struct page` 元数据约占设备容量的 1/64，128 GB 设备需要约 2 GB guest RAM，冷访问还可能增加瞬时 CPU 开销。
- **DAMON + balloon free-page reporting**：先识别并回收冷文件页，再把 guest 空闲页报告给 host，通过 `MADV_DONTNEED` 归还物理内存。主要用于较大可写盘相关内存；与共享只读页解决不同浪费。
- **SCHED_IDLE + core scheduling**：best-effort 工作降优先级，再限制其与 latency-sensitive 任务共用 SMT sibling；只降优先级不足以消除物理核内干扰。内存带宽、LLC 与全核 turbo 降频仍会带来影响。

### 3.4 Rollout 与 GPU 任务生命周期解耦（§6.1–6.3，pp.17–18）

早期 agent loop 与模型服务/RL 框架同处 GPU pod。GPU 被抢占后，沙箱还在，agent loop 却丢失；恢复需通过 command log 对账，已完成命令复用记录结果，避免重复执行非幂等操作。

从 DeepSeek-V4.1 起，**worker container 与 agent sandbox 都移到 GPU 抢占池外**：前者管理 rollout，后者运行 scaffold 和工具，二者共同成为 rollout 状态的唯一权威来源。GPU 任务重启后重连，不必重建整个命令历史。

GPU 任务暂停时，RL 框架主动请求暂停关联沙箱以释放内存：

- container：`docker pause` 冻结进程树，配合 `memory.swap.max` 和 `memory.reclaim` 回收；恢复时先 `MADV_WILLNEED` 预取，再 unpause。
- microVM：保存内存与执行状态快照，终止 Firecracker 进程；恢复时新建进程并加载快照。两类后端均可在后续请求到来时透明恢复。

另一个接口 `pack_diff` 生成增量**磁盘**快照，使 Agent 构建的环境变成可复用资产；它与保留进程/内存的 pause/resume 不是同一层快照。构建账号与执行账号隔离，并在打包前清理残留答案，避免参考解泄漏进训练环境。

### 3.5 任务完整性也是基础设施职责（§6.4–6.5）

生产中出现过从管理日志寻找答案、伪造内部 socket 请求、借包镜像获取参考实现，以及普通命令触发内核缺陷、无限 stdout 占满存储。DSec 使用 AppArmor 控制文件/socket，eBPF 按任务许可过滤 IP、端口和协议，并持续观测失效案例。作者明确指出，这些措施只缓解部分 reward hacking，不能防御任意破坏行为。

## 4. 实验与结果（§8，pp.21–24）

独立 10 节点 CPU 集群使用 AMD EPYC 9655。microVM 直接跑裸机，节点为双路 96 核、每核 2 SMT、1.5 TB DRAM；容器实验跑在 QEMU VM 中，分配 192 hardware threads、512 GB RAM。任务来自真实 RL/评测负载，包含内部 SWE、SWE-bench、Terminal-Bench 和安全任务。**本节不评估第 6 节的 RL 生命周期集成。**

| 机制与对照 | 作者报告结果 | 正确解释 |
|---|---|---|
| 8,192 容器突发：按需 EROFS vs 冷 Docker pull（图 10） | 完成约 35 分钟 vs 超过 60 分钟；单节点累计写盘约 700 GB vs 超过 1,600 GB，约减少 57% | 接近完全本地缓存基线，不是任意训练任务均加速 1.71 倍 |
| EROFS 层挂载 vs 每沙箱解压 tar.gz（图 11） | 完成 45 vs 79 分钟，1.76 倍加速；tar 总写流量约为 5.5 倍、峰值写吞吐约为 3.4 倍 | 用预录确定性工具序列替换 LLM 生成，以隔离环境准备差异 |
| virtio-pmem + DAX vs 无优化（图 12） | host 峰值内存减少 40.2%；瞬时 CPU 峰值从 26.5% 升到 41.4% | 内存改善伴随冷访问 CPU 代价 |
| DAMON + balloon FPR vs 无优化（图 12） | 时间积分 host 内存消耗减少 21.2%，峰值大致不变 | 21.2% 不是峰值降幅 |
| 50% BE 共置负载下 CPU QoS（图 13） | LS chess 单步延迟相对无共置基线的增幅，从 45.2% 降到 17.3% | 减少 SMT 干扰，但未消除所有共享资源竞争 |

各实验、生产部署与不同 baseline 的收益不能相乘为“整体 RL 提速倍数”。报告未给出这些机制对训练收敛、最终模型能力或整体 GPU 利用率的端到端因果量化。

## 5. 结论与局限

DSec 的贡献主要是负载分析、已有操作系统/存储机制的组合，以及与 RL 生命周期协同，而非发明新的隔离原语。

**笔者判断：** GPU 抢占与有状态 rollout 解耦很有价值，但报告没有给出 worker/edge 故障、节点本地可写层丢失、外部服务状态或网络连接失效时的完整恢复协议。GPU 抢占恢复不能外推成任意故障下零状态丢失。3FS、共享存储与特定内核配置也构成复现成本；公开存储组件不能替代完整控制面、策略和训练框架集成。

安全部分属于生产失效经验与缓解措施，未给出攻击成功率降低的受控实验；暂停/恢复也未报告恢复延迟分布及失效率。应将这些设计说明与第 8 节已量化的性能结果分开。

## 6. 个人评述与启发

1. **状态归属比“重启更快”更关键。** 分别明确模型/优化器、rollout 控制流、沙箱文件与进程的状态所有者，避免恢复时重复执行副作用。由 command-log 对账改为外置 rollout 状态，是本文最值得借鉴的变化。
2. **先看真实负载，再决定超卖与缓存。** 低平均 CPU 不代表低内存占用；应测量生成等待时间、sandbox CPU burst、内存驻留时间、镜像访问比例，再选 DAX/FPR/按需加载组合。
3. **环境层独立版本化有助于复现配置。** base/workspace/toolkit 解耦便于记录一次 rollout 的完整环境版本，但版本固定仍不能保证外部网络内容和执行结果确定。
4. **与训练数值确定性分开验收。** 本文主要保证状态连续性和有效执行；“暂停后能继续”“工具日志可重放”都不等于梯度、优化器或训练结果逐位一致。后者仍需固定 RNG、数值内核、数据顺序及通信归约。
