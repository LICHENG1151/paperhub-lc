# 2026 · MiniCPM-o 4.5：面向实时全双工的全模态交互

## 1. 一句话总结 ★

MiniCPM-o 4.5 是一个 **9B 开源全模态大模型**，核心贡献是把多模态交互从"感知与响应交替进行的回合制"升级为 **实时全双工（full-duplex）**——**边看、边听、边说同时进行**，并能基于对场景的持续理解**主动**发起提醒/解说。支撑它的关键技术是 **Omni-Flow**：一个借鉴**时分复用（TDM）**思想、把连续交互切成细粒度时间窗（chunk）、在**共享时间轴**上对齐全模态输入输出流的统一流式框架。它在 9B 规模上视觉-语言能力**逼近 Gemini 2.5 Flash**、全模态理解与语音生成**超过 Qwen3-Omni-30B-A3B**，且能在 **<12GB 内存**的边缘设备上实时跑起来。

## 2. 背景与问题

作者主张：迈向"类人交互"的瓶颈**已不再是模态覆盖或延迟本身，而是交互范式**。现有 MLLM 有两个结构性缺陷：

| 缺陷 | 表现 | 后果 |
|------|------|------|
| 感知/响应**相位分离** | 先感知、后回答，两阶段交替（blocked I/O） | 生成过程中**无法吸收新到达的信息**做实时调整 |
| 行为**纯被动（reactive）** | 只在用户显式请求时才响应 | 无法从"持续演化的环境"中**主动**发起行为 |

要达成类人交互，需要两点：① 感知与响应在 **token 级、沿时间持续耦合**（听/看/说/写并行，而非串行流水线）；② 交互**由上下文驱动**而非纯触发式（不等用户开口，也能主动做实时场景描述/提醒）。

## 3. 核心思想 ★ —— Omni-Flow

**把"回合"拆成"时间窗流"**。Omni-Flow 借时分复用思想，把连续交互划成时长为 `t` 的细粒度 chunk；每个窗内**先吃新到的感知信号、再产出本窗输出**，于是回合制变成"逐窗时间-局部更新流"。当 `t` 足够小，感知与响应在时间上紧耦合，**自然逼近全双工**。三个要点：

1. **三条时间对齐流**：`env-visual`（环境视觉）、`env-audio`（声学场景，含用户语音）、`out-stream`（助手文本+语音输出）。**关键视角转换**：用户请求不再是"特权对话角色"，而是**并入被持续观测的世界状态**（主要从 env-audio 进入）；模型不靠显式请求触发，out-stream 随感知持续演化。→ 模型处于**常开环境**，要自己决定**输出什么 / 是否输出 / 何时输出**。
2. **统一序列化**：第 k 个时间块把三流编码为 `g_k = [v_k; a_k; o_k]`，顺序拼接成单条因果序列喂给标准 LLM；**无需输出时 `o_k` 只放一个 `[listen]` 特殊 token**。因为每窗自行决定是否发声，**天然支持主动行为、并减少对外部 VAD 的依赖**。
3. **设计权衡（消融，Table 1）**：三个维度实测结论——
   - **时间粒度**：chunk 越小越及时，但每窗建模预算越少；**1.0s 最平衡**（0.2s/0.1s 显著劣化）。
   - **边界显式性**：**显式**标注组边界更好（帮模型区分"新观测"与"新生成"）。
   - **控制表述**：**Listen-Speak（先预测二元 listen/speak 控制 token，再生成内容）> Listen-Text（在共享输出空间直接预测 [listen] 或文本）**——"是否说"应与"说什么"解耦。

## 4. 实现细节

### 4.1 端到端全模态架构（~9B，token 级可微连接）

| 组件 | 选型/规格 | 关键设计 |
|------|-----------|----------|
| 视觉编码 | SigLIP ViT 0.4B + LLaVA-UHD 切片 + resampler | **16× token 压缩**（高于常见 4×）；全双工流式用 448²、否则 2240² |
| 音频编码 | Whisper Medium 0.3B，chunk 流式 | 50 特征 token/s → MLP 做 **5× 时间压缩 → 10 audio token/s** |
| LLM 骨干 | **Qwen3-8B** | **只在文本域出 token**，实时全双工仅需 **3–4 解码步/s**（=人说话速度），避免直接产语音 token（~25/s）拖慢并损伤语言能力 |
| 语音 token | 轻量 **Llama 语音解码器 ~0.3B** | 对每个文本 token，**叠加 LLM 骨干隐状态**（MLP 重塑）→ 生成 S3 语音 token；韵律由骨干预编码，小解码器专注语音建模 |
| 波形合成 | 流式 **flow-matching** 解码器 | 依据系统提示中的**参考音频**把 S3 token 转波形（支持 voice cloning） |

> 骨干"留在文本域、把语音 token 外包给小解码器"是效率与能力兼得的关键取舍。

### 4.2 TAIL —— 时间对齐交织，保证语音"不滞后"

问题：文本生成时长 ≠ 语音播放时长，若某段文本要花更久才念完，语音流会**逐渐落后于模型当前状态**，听到的音频对应的是很早之前生成的文本（stale）。

**TAIL（Time-Aligned Interleaving）**：按 chunk **自适应决定本步生成多少文本**，让"念完新内容后语音进度逼近当前时间边界 kt"；若前面已积累延迟，就少生成文本让语音追上。训练监督来自全双工数据里每个文本 token 的起止时刻（落在 `[(k-1)t, kt)` 的文本 token 及其语音 token 归入第 k 块）。另设**有界 look-ahead**：把每块最后几个文本 token 的语音推迟到 k+1 块，兼顾发音上下文（如 "the apple" vs "the car"）又不让文本跑太前。

### 4.3 训练四阶段

1. **语音预训练**：冻结骨干（保视觉/语言能力），只训新增语音模块（audio projector / LLM→speech projector / speech decoder），对齐 Whisper 特征到 LLM 隐空间。
2. **联合预训练**：全解冻，VL+语音+全模态**均衡混合**；不同数据并行 rank 分配不同模态组合以固定每步配比；统一 next-token 目标。
3. **联合 SFT**：大规模指令微调 + 高质量人标微调两阶段；数据用 0.2–0.4MP 变分辨率、1–5 FPS 变帧率增广，支持推理期质量/效率权衡。
4. **RL**：GRPO 提升推理与指令遵循；引入**平滑长度奖励**（改自 Kimi-K1.5，前 480 步不加）；RLAIF-V 降幻觉（图文习得的降幻觉能力可迁移到流式全双工）。

## 5. 实验与结果

- **视觉-语言**（Table 2/3）：9B 规模，OpenCompass **77.6（instruct）/78.2（thinking）**，稳超 InternVL3.5-8B、Qwen3-VL-8B 乃至 Qwen3-Omni-30B，逼近 Gemini 2.5 Flash / GPT-5。**文档解析最强**：OmniDocBench EN 0.109 / CN 0.162（越低越好），显著优于更大的 Qwen3-Omni-30B。
- **语音**（Table 4/5）：ASR 接近头部（GigaSpeech/VoxPopuli 最好）；语义类**领先**（CoVoST2 en→zh、MELD、VoiceBench AlpacaEval、Speech TriviaQA）；语音生成 SeedTTS ZH/EN CER/WER 最低、Expresso/ESD 情感风格控制最佳。
- **文本**（Table 6）：多数任务**超过其骨干 Qwen3-8B-Instruct**（均分 82.1 vs 81.6），说明全模态训练**未牺牲**文本能力。
- **全模态理解**（Table 7）：7 个基准中 5 个最佳（Daily-Omni、WorldSense、Video-Holmes、JointAVBench、AVUT-Human）。
- **全双工**（Table 8）：LiveSports-3K-CC 胜率 **54.4**，比 LiveCC/StreamingVLM 高 **+12.9 / +8.8**。
- **效率**（Table 11/12）：RTX 4090 上 INT4 **212 tokens/s、11GB、首 token 0.58s**（同条件 Qwen3-Omni-30B BF16 直接 OOM）；自研 **llama.cpp-omni** 框架 RTF **0.20–0.27**，跨 macOS/Windows/Linux 与 DGX Spark，**<12GB 内存**边缘可跑。

## 6. 结论与局限

**结论**：MiniCPM-o 4.5 = 首个可边缘运行的全双工全模态 9B 开源 MLLM；Omni-Flow 提供了"全双工 + 主动"交互的通用建模范式（共享时间轴对齐 I/O）。同时兼容传统回合制，可在两种模式间切换。

**局限（作者自述）**：① 长时段、动态真实流式交互下的基础能力与鲁棒性待验证；② 流式模式语音生成偶有不稳（发音错误、中英夹杂 code-mixing）；③ Web demo 受网络影响有延迟/丢帧（本地 llama.cpp-omni 更稳）；④ **主动行为仍偏简单**，更丰富的情境感知规划与自发协助留待后续。

## 7. 个人评述与启发 ★

1. **"范式"而非"指标"是主线，值得借鉴其问题框定**：论文把瓶颈从"模态/延迟"重定义为"交互范式"，进而拿出 Omni-Flow。这种"先换视角、再给机制"的叙事，比堆 benchmark 更有说服力——**把用户请求降格为世界状态的一部分**是最锋利的一刀，直接让"主动性"从架构里自然长出来，而非外挂一个触发器。
2. **时分复用 → 流式对齐，是很"系统"的思路**：把连续交互切成固定时间窗、窗内"先感知后输出"、无输出就发 `[listen]`——本质是**把实时性问题转成序列化 schema 设计**。chunk=1.0s 的甜点、显式边界、控制与内容解耦（LS>LT）这三条消融结论，很像我们做流水线/调度时"粒度 vs 每步预算"的经典权衡，可迁移到**流式推理服务的批处理窗设计**。
3. **TAIL 击中的是"生成时钟 ≠ 播放时钟"漂移**——这与训练/推理系统里**producer/consumer 速率失配**、KV/ckpt **搬运滞后**是同构问题：用"累计进度对齐目标边界 + 有界 look-ahead"做自适应节流，是一个干净的反馈控制范式，值得在我们"cadence 而非峰值带宽才是约束"的场景里借用。
4. **"骨干只出文本、语音外包给小解码器"是漂亮的能力-效率解耦**：既把骨干解码步压到 3–4/s（人语速），又避免直接产语音 token 损伤语言能力；同时 16× 视觉压缩 + 5× 音频压缩把 token 预算摁住。**边缘 <12GB、4090 INT4 212 tok/s** 的工程结果说明"小而对"的架构选型比单纯堆参数更重要。
5. **对我们的直接价值**：若要评测/自建**流式全模态或实时语音**系统，Omni-Flow 的序列化格式、TAIL 的对齐监督构造、以及"RTF/首 token 延迟/内存"三件套的效率口径，都是可直接复用的**测法与指标框架**；其自曝的"中英夹杂/长时漂移"也提示了压测应重点覆盖的失败模式。

## 9. 术语表

| 术语 | 含义 |
|------|------|
| Full-duplex（全双工） | 感知与响应同时进行，边听边看边说，对比回合制半双工 |
| Omni-Flow | 本文框架：时分复用切窗 + 共享时间轴对齐全模态 I/O |
| `[listen]` token | 某时间窗无需输出时的占位输出，模型自决是否发声 |
| env-visual/env-audio/out-stream | 三条时间对齐流：环境视觉/声学场景/助手输出 |
| TAIL | Time-Aligned Interleaving，自适应文本-语音交织，防语音滞后 |
| LS / LT | Listen-Speak（控制与内容解耦）/ Listen-Text（共享输出空间），LS 更优 |
| S3 token | 语音离散 token 表示，供 flow-matching 解码为波形 |
| RTF | Real-Time Factor，<1 即快于实时，越低越高效 |
| VAD | Voice Activity Detection，传统语音活动检测模块 |
