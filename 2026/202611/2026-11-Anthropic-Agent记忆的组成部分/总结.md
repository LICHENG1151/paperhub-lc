# The components of agent memory · 总结

## 一句话总结 ★

Anthropic 官方博文：把 agent 记忆拆成「会话内记笔记 + 空闲期 dreaming（回放日志、纠错、建 wiki、按目标重组）」两半，类比人脑「海马体快速记 + 睡眠期固化到新皮层」；核心结论是——模型越强越会自己判断什么值得记，提前定死记什么反而拖后腿。

## 背景与问题

- 做长任务的 agent 需要跨 session 保留经验，但「什么时候记、记什么、怎么保持不过期」没有公认答案。
- 作者把 agent memory 的边界先划清：**Claude 从经验中获得、跨 session 保留、之后能读回来的知识**。不含三种近邻：改 weights、单次会话内的 in-context learning、compaction（用摘要替换旧对话来续 context window）。
- 类比人脑：经验先由海马体即时编码，睡眠/静息时回放（replay）并固化到新皮层。agent 对应做法：会话内写日志和 memory notes，空闲时用 dreaming（借用 Letta / UC Berkeley 的 sleep-time compute 概念）对日志回放、整理记忆。

## 核心思想 ★

整篇文章围绕「记忆不是一个东西，是一组组件」展开，可归成四类：

1. **会话内记笔记（memory notes）**：Claude 在干活当下把判断为「显著」的事件写进记忆库（如一个 memory notes 文件夹）。难点是：当下并不知道后面会用到什么。
2. **记忆 = 对未来的预测**：写下一条 rule，等于预测这个模式以后还会用到。写一条已验证的事实，等于预测以后的 session 可以直接信它、不用再查。
3. **dreaming（离线整理）**：空闲期让 Claude 回放日志，做四件事——
   - **纠错**：拿原始 transcript 当 ground truth，检查笔记是否写错/过时并改写；
   - **建表示**：维护 wiki（互相链接的页面），给不断增长的知识库当「地图」；
   - **上浮**：把高频要用的笔记提升到记忆层级顶端，由 harness 在每个 session 开始时注入 context；
   - **补缺**：跨多个 session 找公共模式、补悬空链接、修共性问题。
4. **按目标塑形**：dreaming 的指令可以围绕特定目标调（比如围绕「服务好这个人」组织记忆）。

## 实现细节

- 实验载体是 **Claude Managed Agents**：每个问题/session 冷启动，唯一跨 session 的东西是一个持久化的 memory 文件夹（可读可写）。
- **对记忆的引导方式**：只告诉 Claude「有个 memory 文件夹可用」这种泛化提示，不规定记什么、怎么记；最强模型这样就够。
- **层级注入要克制**：注入的笔记吃 token、错笔记会污染每个 session、指令越长 adherence 越降（引 Claude Code 文档）。所以顶层必须小，dreaming 的一部分工作就是把细节下沉、只留链接。
- **Claude Code 的 auto memory 就是这个设计**：每个 session 只加载 `MEMORY.md` 的前 200 行 / 25 KB 当索引，让 Claude 知道自己知道什么、去哪里找。

## 实验与结果

### 实验 1：CL-Bench 1.0 —— 记忆能不能形成学习闭环

任务形态：查数据库答题 → 被告知正确答案 → 可以写 memory 供后续 session 用。能否形成「记失败 → 提理论 → 验证 → 固化成 rule」的闭环，各代模型差别很大：

| 模型 | 闭环做到哪一步 |
|---|---|
| Sonnet 4.6 | 能提出「为什么错」的理论，但散落一堆文件、全是未验证的猜测 |
| Opus 4.7 | 合并成单一参考文档，开始标注「已核实 / 未确认」 |
| Sonnet 5 | 答案被批改后标记 confirmed，答错会写更正 |
| Opus 5 | 首个闭环模型：大部分条目带 rule + 依据 + 陷阱警告 |
| Opus 5.5 / Sonnet 5.5 | 同样闭环，无 memory 的基线更高，加 memory 后与 Opus 5 相当 |

### 实验 2：Pokémon Red —— 显著性判断（什么值得记）

| 模型 | 记忆规模 | 战绩 |
|---|---|---|
| Sonnet 3.7 | 225 个文件夹、413 个文件（每场战斗/每件道具单独建档） | 1 个 badge |
| Fable 5 | 2 个文件夹、9 个文件 + 顶层 `global.md` | 4 个 badge |
| Opus 5.5 | 小文件夹，边玩边重写当前目标与下一步 | 通关 |

- Sonnet 3.7 的问题：游戏状态天天变，详尽记录持续过期；约 10000 步时曾连续 17 步只在建/删第 4 个「master」文件夹、没在游戏里做任何动作。
- Fable 5 只记「屏幕上读不出来的东西」：策略、计划、验证过的 rule（例：连续 3+ 个 Poké Ball 失败就改变按键节奏——实测有效）。`global.md` 当 dashboard：当前目标、打道馆预案、使用记忆的自有规则。
- 教训：**能从环境读到的信息不值得存**（钱数、地图位置），只有 agent 自己推导出来、不写下来就丢的东西才值得存。

### 实验 3：引导方式 —— 定死规则 vs 放手

- 「只记失败」这类硬规则让 Opus 5 / Opus 4.7 丢掉了 memory 带来的大部分收益。对强模型，**给判断自由 > 预设固定规则**。
- 引导对老模型帮助最大：提示 Sonnet 4.6「答题前先读 memory、明确验证理论」几乎让分数翻倍；Sonnet 5 不用提示，10 次里 9 次自己先读记忆。

### 实验 4：dreaming 纠错 —— Mt. Moon 单向崖陷阱

- Claude 误记 PokéCenter 在山洞东侧 → 走出 PokéCenter 时误判「Mt Moon 已过」→ 掉下单向崖回到原路，且导航工具不显示落差，归因也错。
- 未纠错的一轮：连掉 3 次后写「我要停下来了」，被自动回复要求继续，最终退回前一个城镇，没到 Cerulean City。
- 对同一记忆文件夹跑 dreaming：对照 transcript 发现笔记错了并改写 → 修正后直接重回 Mt. Moon、抵达 Cerulean City。

### 实验 5：dreaming 建 wiki —— Stainless 语料

语料：收购来的 Stainless 内部文档，约 35 万文件 / 420M token；25 道题 + 一个搜索工具；128 个 Opus 5 dreaming session 增量建 wiki。

| 记忆配置 | 得分（按评分点） |
|---|---|
| 仅 dreaming 2 个 session | 13% |
| 仅 dreaming 128 个 session（只准用 wiki 答题） | 48% |
| 仅搜索工具 | 53% |
| 搜索 + wiki（wiki 从小长大） | 54% → 61% |

- 搜索 + wiki 还省 token：每题约省 20000。
- wiki 是增量生长的：早期像新员工，dreaming 轮次多了像老员工。

### 实验 6：wiki 何时有用 —— Harvey LAB + 并购文档

- 24 道并购问答题（多半要跨文档拼信息、用判断或算术）：跨文档/判断类 wiki 87% vs 仅搜索 73%。
- 反例一：某 LAB 任务的评分点大多能从单一文档文本检索直接拿到，wiki 无明显增益。
- 反例二：某任务 wiki 长得比原文档还大——引 Borges《论科学的精确性》（地图大到等于疆域本身），等于什么都没抽象。

### 实验 7：按目标塑形 —— 共享表并发覆盖问题

- 初始指令没说「合同条款是重点」：多个 agent 同时写共享条款表，互相覆盖 → 生成的 brief 只覆盖 41/57 评分点（72%）。
- 跑一个反思循环（Claude 反思失败 → 改写建 wiki 的指令 → 重建）：每份合同单独一页、逐字引用条款而非摘要 → 100%。

## 结论与局限

作者自己列的开放问题：

1. **何时创建记忆**：会话内即时写会分心，dreaming 后台写又不能立即可用；两者是权衡。
2. **如何保鲜**：记忆会写错、会随环境漂移；dreaming 能修但要花 compute，持续全量核对不现实，可能要按「易变程度 / 访问频率」调 dreaming 节奏。
3. **transcript 搜索 vs 表示**：搜索可以当地基，表示（wiki）要花 compute 维护、防止积累错误与幻觉。
4. 前沿模型的显著性判断虽在进步，但**没有任何模型能预知未来几轮会需要什么**——dreaming 的价值就是「事后向回看」。

局限（我读到的）：全文是工程博客体，无公式、无开源实现；样本多为「一轮实测 + 现象描述」（如 Pokémon 只各跑一轮），不是严格受控实验；各 benchmark 得分口径是「评分点覆盖率」，绝对值不可跨实验比较。

## 个人评述与启发 ★

- **「引导强模型要少、引导弱模型要多」是这篇最反直觉的可操作结论**：给 Sonnet 4.6 明确步骤分数翻倍，给 Opus 5 定「只记失败」反而掉分。落到我们自己的 agent 工程：prompt 里预设记忆规则前，先想想模型本身是否会判断；版本越新，规则越该往「说清目的」退。
- **「屏幕上读得到的不要存」是很好的通用判据**：可从环境重新获取的信息（状态类）不值得占记忆；只有推导产物（策略、验证过的 rule、教训）才值得。这也解释了为什么记忆要小——大而全的档案库维护成本会吃掉主任务。
- **dreaming = 用 compute 换记忆质量**：纠错靠 transcript 当 ground truth、建 wiki 靠多轮增量、并发写共享结构要防互相覆盖（每合同一页、逐字引用 > 共享摘要表）。这三条对任何「离线整理日志」的 pipeline 都直接可抄。
- **与 Claude Code auto memory 互为印证**：本文官方点名了本会话正在用的这套机制——`MEMORY.md` 前 200 行 / 25 KB 做索引、正文按条放独立文件、链接 `[[name]]` 组织。等于 Anthropic 把自己产品里的设计 rationale 写了出来，对维护我们这份 memory 索引有直接参考价值（顶层小、只放指针、细节下沉）。
- **对我们 ltp_ha / 运维 agent 的启发**：训练任务的 console 日志全量在 PVC，等于天然 transcript；「空闲期对日志跑 dreaming 提炼案例库 / 运维手册」与本文的 Stainless wiki 场景同构，只是规模和节奏要按日志增速调。

## 术语表

| 术语 | 含义 |
|---|---|
| agent memory | Claude 从经验获得、跨 session 保留、之后能读回的知识；不含改 weights / in-context learning / compaction |
| dreaming | 空闲期让模型回放自己的日志/转录，对记忆做纠错、建表示、上浮、补缺的离线整理过程 |
| memory notes | 会话内即时写下的记忆条目，通常存成一个文件夹里的文件 |
| salience（显著性） | 「这件事值不值得记」的判断；文中核心论点是这项能力随模型代际显著增强 |
| wiki | Claude 自己写并维护的互相链接的页面集，用于在增长的知识库里导航定位 |
| compaction | 用摘要替换旧对话轮次以续接 context window 的机制（不属于本文定义的 memory） |
| replay | 人脑睡眠期回放近期经验并固化的过程，dreaming 的生物类比 |
